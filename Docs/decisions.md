# Журнал архитектурных решений

Формат: номер, дата, решение, почему, что это меняет. Решения принимались
по итогам разбора брифа (`Docs/brief.md`), четырёх независимых
архитектурных проработок (линзы: iOS-native, платформа коннекторов,
алгоритмы, тестируемость) и судейства по критериям «соответствие брифу»,
«расширяемость», «реализуемость в текущем репозитории», «простота»,
«корректность модели здоровья».

## ADR-001 · 2026-09-10 · Intelligence живёт на устройстве, ядро — Foundation-only Swift

**Решение.** State/Decision/Nudge/Feedback Engine — чистый Swift в
`Linea/Core`, без Apple-фреймворков. Сервер в v1 не принимает решений; его
единственная будущая роль — прокси к облачной LLM (`POST /v1/explain`).

**Почему.** Данные HealthKit доступны только на устройстве; стек сервера в
репозитории не выбран; приватность и офлайн; бриф описывает Swift-структуру
внутри приложения; ядро можно собирать и тестировать в Docker без Xcode.

**Меняет.** Backend/ остаётся заглушкой; `API/openapi.yaml` получает путь
только вместе с реализацией облачного объяснителя.

## ADR-002 · 2026-09-10 · Двойная компиляция ядра: Xcode и SwiftPM с паритетом настроек

**Решение.** `Package.swift` в корне с `path: "Linea/Core"` и настройками,
повторяющими pbxproj (default isolation MainActor, language mode 5,
MemberImportVisibility, пять фич Approachable Concurrency). Тесты в
`Tests/` вне `Linea/`. Xcode подхватывает `Linea/Core` через synchronized
group; pbxproj не правится.

**Почему.** Разработка идёт на Linux; вариант `sources: ["Domain",
"Intelligence"]` даёт предупреждения на каждый SwiftUI-файл; тесты внутри
`Linea/` попали бы в app-таргет. Паритет настроек — чтобы семантика
изоляции не расходилась между двумя «домами» кода.

**Меняет.** Появляется папка `Linea/Core` (отклонение от брифа на один
уровень; внутри имена брифа сохранены). `Scripts/test-core.sh`,
`Scripts/check-layers.sh`, CI на Linux — блокирующий.

## ADR-003 · 2026-09-10 · Все типы ядра `nonisolated` + `Sendable`

**Решение.** Каждый тип и протокол в `Linea/Core` объявлен `nonisolated`;
движки — `nonisolated struct: Sendable`. Store'ы и `Local*Repository`
остаются `@MainActor`.

**Почему.** При `SWIFT_DEFAULT_ACTOR_ISOLATION = MainActor` любой
неаннотированный тип становится MainActor-изолированным: провайдеры в
TaskGroup выполнялись бы последовательно, а тесты требовали бы `@MainActor`.

## ADR-004 · 2026-09-10 · Время только через `TimeContext`

**Решение.** Движки не вызывают `Date()`, `Calendar.current`,
`TimeZone.current`, `Locale.current`; всё приходит в `TimeContext { now,
calendar, locale }`. `TimeContext.live` создаётся только в composition
root. Линтер проверяет папки движков.

**Почему.** Контейнер тестов живёт в UTC (проверено: 14:30 МСК = 11:30);
без явного календаря сценарии «до 12:00» и «14:30» невоспроизводимы.

## ADR-005 · 2026-09-10 · `SignalKind` — открытый строковый тип; задачи и цели — не сигналы

**Решение.** `SignalKind` — string-backed struct, коннекторы объявляют
свои виды в `extension SignalKind` у себя. Задачи, цели, профиль — типизированные
поля `ContextSnapshot`. Исключение: задача с `scheduledStart` становится
`Commitment`.

**Почему.** Движки подписаны на виды сигналов, а не на провайдеров — новый
носимый с тем же `health.sleep.segment` подхватывается без правок. Задачи —
предмет решения, а не измерение; `TasksProvider` дублировал бы данные.

## ADR-006 · 2026-09-10 · Контракт `ContextProvider` с явным запросом и статусом

**Решение.** `fetchContext(ContextRequest{day, time, historyDays}) ->
ProviderFetchResult{signals, status}`; `ProviderStatus` включает
`.indeterminate` (HealthKit не раскрывает read-доступ). Ошибка провайдера →
`.failed`, снапшот всё равно собирается. Курсоры, потоки изменений, реестр —
не в v1.

**Почему.** Сигнатура брифа без параметров заставила бы провайдер читать
`Date()`; статус нужен, чтобы честно показывать «нет данных о сне».

## ADR-007 · 2026-09-10 · Четыре оси расширения, фиксированная формула scoring

**Решение.** Коннектор может добавить `ContextProvider`, `StateAnalyzer`
(компонент состояния с весом), `PlanRule` (пост-обработка плана),
`NudgeRule`. Пять компонент scoring из брифа фиксированы; протокола
«ScoringFactor» нет.

**Почему.** Веса должны суммироваться в осмысленную единицу; коннекторы
влияют через состояние (энергия) и правила, а не через новые слагаемые.

## ADR-008 · 2026-09-10 · Робастные baseline и раздельные сон/восстановление

**Решение.** Медиана/MAD за 28 дней с абсолютными полами, `isReliable = n ≥
7`, HRV в ln-шкале по ночной медиане; `sleep` и `recovery` — отдельные
компоненты, свёртка с confidence и сжатием к 0.5; асимметричный
`energyFit` с `capacity = (0.5 + 0.5·energy)·alertness(t)`.

**Почему.** Устойчивость к одной «пьяной» ночи и редким сэмплам; бриф
разводит «Сон 6:03» и «Recovery ниже обычного»; плохой сон не должен
обнулять утро.

## ADR-009 · 2026-09-10 · План — отдельная сущность, JSON-блоб

**Решение.** `DayPlan` хранится в `DayRecord` как JSON; «Принять план» и
пересчёт не меняют задачи; «Перенести» меняет `task.date` через
существующий `PlanStore`.

**Почему.** Чистая история «план vs факт» для калибровки; эволюция
структуры плана без миграций SwiftData, которые нельзя проверить на Linux.

## ADR-010 · 2026-09-10 · Нудж 14:30 — предрасчитанные локальные уведомления, без фоновых задач

**Решение.** При «Принять план» нуджи с готовым текстом и действиями
планируются как локальные уведомления, отменяются при выполнении задачи,
пересчитываются при каждом открытии. `BGTaskScheduler` — v1.1.

**Почему.** iOS не исполняет код «в 14:30»; текст детерминирован принятым
планом и обязательствами; фоновые задачи требуют настроек таргета на Mac.

## ADR-011 · 2026-09-10 · LLM только формулирует; шаблоны — источник истины

**Решение.** `RuleBasedExplainer` (детерминированные русские шаблоны из
типизированных `Fact`) всегда доступен и закреплён golden-тестами. LLM
(on-device FoundationModels, позже облако) может переписать текст только
после валидатора (числа ⊆ фактов, кириллица, стоп-слова).

**Почему.** Русский язык on-device модели не гарантирован; тексты брифа
целиком собираются шаблонами; решения о плане принимает код.

## ADR-012 · 2026-09-10 · Feedback Engine пересчитывает калибровку из истории, веса не учит

**Решение.** `Calibration` = функция от последних 14 дней `DayRecord`
(идемпотентно), ограниченный набор регуляторов с границами и журналом
изменений. Веса scoring логируются в `ScoreBreakdown`, не обучаются.

**Почему.** Три кнопки в день не идентифицируют пять весов; объяснимость
важнее адаптивности.

## ADR-013 · 2026-09-10 · `HealthKitManager.swift` остаётся в корне до PR на Mac

**Решение.** Файл явно прописан в pbxproj (строки 10, 15, 42, 128) и не
перемещается; новая HealthKit-логика — отдельные типы и extension-файлы в
`Linea/Data/HealthKit`. Перенос — отдельный PR с проверкой в Xcode.

**Почему.** Единственная операция, которую нельзя проверить на Linux.

## ADR-014 · 2026-09-10 · Аддитивная персистентность без VersionedSchema

**Решение.** Новые поля `TaskEntity`/`GoalEntity` — optional/с дефолтом
(lightweight-миграция); новые сущности — JSON-блобы со `schemaVersion`.
`VersionedSchema` — при первом неаддитивном изменении.

**Почему.** Mac-only код, который нельзя проверить здесь; пока не нужен.

## ADR-015 · 2026-09-10 · Питание в v1: профиль + окна еды + правило + «Поел»

**Решение.** Без каталога, рецептов и калорий. Заболевания — только теги-
фильтры без интерпретации. Окна еды — обязательства; `NutritionRule` даёт
рекомендацию при сниженной нагрузке и перед тренировкой.

**Почему.** Минимум, при котором питание реально влияет на план (критерий
успеха), без внешней базы и бэкенда.
